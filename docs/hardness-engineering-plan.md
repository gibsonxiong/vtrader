# Hardness Engineering 方案

## 1. 定义

本文将 `Hardness Engineering` 解释为：

- 让系统更难被误用
- 让关键流程更难被绕过
- 让高成本操作更难被无意触发
- 让异常路径更容易暴露、恢复和诊断

这不是单纯的“安全加固”，而是覆盖认证、输入、状态流转、任务保护、运行时可观测性的综合工程实践。

## 2. 本项目的硬度目标

### 目标一：环境边界清晰

任何开发者都应能快速回答以下问题：

- 当前页面请求的是 Mock 还是真实后端
- 当前登录态来源于哪个服务
- 当前 WebSocket 连的是哪个服务

### 目标二：认证失败可恢复

任何认证失败都应进入统一恢复流程，而不是散落成局部错误提示。

### 目标三：高成本操作可控

回测、批量下载、订阅等操作都应具备：

- 输入约束
- 幂等控制
- 并发上限
- 失败恢复

### 目标四：问题可诊断

当 Redis、Mock、后端 API、WebSocket 任何一环出问题时，系统应能快速暴露故障点。

## 3. 优先级路线图

## P0

### 3.1 统一 API 入口策略

问题：

- 前端默认 `/api` 走 Mock
- 部分真实交易请求又直接访问 `3000`

结果：

- 调试边界模糊
- 登录态和数据源容易错位

建议：

- 新增统一环境变量，如：
  - `VITE_API_TARGET=mock|backend`
  - `VITE_TRADE_API_URL=...`
  - `VITE_WS_URL=...`
- 在前端启动日志中明确打印当前命中的 API 与 WS 目标
- 禁止业务代码中硬编码 `http://127.0.0.1:3000`

建议产出：

- 统一的前端环境配置文件
- 启动期配置校验
- API 目标切换说明

### 3.2 统一认证失败语义

问题：

- 有的接口通过 HTTP `401`
- 有的接口通过业务错误体表达未授权

建议：

- 在请求层统一将未授权错误归一化
- 所有认证失败走同一套登出 / 重新登录 / 弹窗恢复流程
- 增加对刷新 token 失败场景的埋点或日志

建议产出：

- 请求层错误归一化约定
- 认证失败测试用例

### 3.3 为 WebSocket 建立保护栏

问题：

- 连接和订阅缺少足够强的保护

建议：

- 对连接增加身份校验
- 对订阅参数增加 DTO/Schema 校验
- 限制单连接订阅数量
- 对重复订阅、恶意订阅、超频订阅加保护

建议产出：

- WebSocket 接入约束文档
- 订阅上限和错误码约定

## P1

### 3.4 为回测任务增加防误用机制

建议：

- 对时间范围、标的数量、参数规模设置硬上限
- 为回测创建接口增加幂等键
- 防止同一用户短时间重复提交相同任务
- 给队列增加最大等待数和拒绝策略
- 为超长任务提供中止或过期机制

建议产出：

- 回测任务约束文档
- 参数边界表
- 队列保护策略

### 3.5 增加启动前健康检查

建议：

- 前端启动时打印当前环境、生效 API、Mock 状态
- 后端启动时检查 Redis、数据库、关键配置
- 对缺失依赖给出明确报错，而不是运行中隐式失败

建议产出：

- 健康检查端点
- 启动前自检脚本

### 3.6 补齐输入校验与异常边界

建议：

- 后端全面接入 DTO + validation pipe
- 统一异常响应结构
- 对批量接口限制分页、条数、时间跨度

建议产出：

- 请求参数校验规范
- 错误码与异常格式规范

## P2

### 3.7 增加可观测性

建议：

- 为认证失败、任务提交、任务执行、WebSocket 订阅增加结构化日志
- 引入 request id / job id / trace id
- 给关键任务链路增加耗时统计

### 3.8 增加面向误操作的前端保护

建议：

- 批量下载、删除、回测启动等操作增加二次确认
- 长耗时任务增加状态提示、取消入口和结果追踪
- 对危险按钮做显式文案区分

## 4. 建议先落地的文件

如果要把 Hardness Engineering 继续落到仓库中，建议优先新增或完善以下文件：

1. `frontend/.env.development.backend`
   用于明确“前端直连真实后端”的开发模式
2. `frontend/src/config/runtime.ts`
   统一暴露 API、WS、Mock、生效环境等运行时配置
3. `backend/src/common/validation.ts`
   统一注册全局校验与异常格式
4. `backend/src/health/health.controller.ts`
   暴露 Redis / DB / Queue 基础健康状态
5. `docs/hardness-engineering-checklist.md`
   作为团队执行清单持续维护

## 5. 落地顺序建议

建议按下面顺序实施：

1. 统一 API / WS / Mock 配置来源
2. 统一认证失败语义
3. 为 WebSocket 和回测接口加参数校验与限流
4. 增加健康检查和结构化日志
5. 补充端到端回归测试

## 6. 验收标准

当以下条件满足时，可认为项目在 Hardness Engineering 上迈过第一阶段：

- 新成员能在 10 分钟内判断当前请求命中了 Mock 还是真实后端
- 所有未授权场景都进入统一恢复流程
- 回测与批量下载具备明确的输入上限与拒绝策略
- WebSocket 订阅具备身份、频率和数量控制
- Redis / DB / API 依赖异常时可以快速定位
